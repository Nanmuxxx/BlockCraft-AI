# Mochi 修改请求标识修复（2026-10-24）

## 已确认原因

统一网关对 `/api/mochi-plan` 强制要求单个有效的 `Idempotency-Key`，
但浏览器 `createHttpPlanProvider` 仅发送了 `Content-Type`。因此，在受统一账本
保护的部署组合中，修改请求会在模型调用和预算预留前被拒绝。
`IDEMPOTENCY_KEY_INVALID` 又被该接口的错误白名单折叠为 `AI_UNAVAILABLE`，
使界面无法区分请求协议错误和模型暂时不可用。

这一缺口由浏览器适配器与真实 HTTP 部署组合的离线测试复现。没有保留用户
截图对应请求的服务端追踪，因此不能据此排除其他请求还会遇到模型格式或网络失败。

## 修复范围

- 每次宿主调用 HTTP 计划适配器时生成一次随机请求标识，并随请求发送。
- 已有宿主继续负责并发去重、复用待确认预览；明确手动重试创建新标识。
- 不添加自动重试；保留服务端重放和内容冲突拒绝规则。
- 将缺失标识、重放及内容冲突映射为固定、脱敏的中文反馈。
- 状态接口正确标识请求绑定的真实模型传输；该标识不代表模型可用性探测。
- 不修改额度、账本、凭据、硬件或部署配置。

## 验证

新增 `tests/mochi-stability/unified-http.test.cjs`，覆盖实际浏览器适配器、
Mochi 宿主、认证 HTTP 服务、持久统一账本和受控模型出口；仅最后的外部网络
请求使用离线响应。使用合成凭据和临时测试账本，不涉及真实付费调用。

验证：只预留和提交一次、预览复用不调用、重放/冲突/缺失标识不收费、
确认前项目不变、确认后仅修改目标表单、无关列表和记录不变、撤销恢复。

回归通过：核心 224、字段/网关 198、受控修改 39、主动建议 70、互动积木 13、
项目 ZIP 35、Mochi 稳定性 25，合计 604 项。TypeScript/Vite 构建通过。

## 限制

未以真实付费模型请求验证上游服务；离线组合通过不能等同于线上模型调用成功。
既有保守意图范围校验、模型输出校验仍然生效。`filter/chart/details` 的直接
Mochi 修改尚未接入，不在本修复中扩大支持范围。
